# 第一部分：快速了解（读这一页就够）

## 做完了什么

把仿真里已经跑通完整避障的导航栈搬到了真机工作区，通信层从 PX4 DDS 全部换成
MAVROS，并补上真机必须有的外部视觉健康门禁。

搬过来的能力：

- **Super A\* 全局规划** —— A\* 搜索 + Chaikin 平滑 + 净空校验 + 窄通道居中
- **EGO B-spline 局部避障** —— 实时点云 + 静态地图融合，B-spline 轨迹优化
- **四点任务序列器** —— A → B1 → B2(悬停+识别) → C → D(悬停+识别)
- **目标识别接入** —— YOLOv8 四模型级联，只在计分区运行

融合前 `ws_offboard_control` 只能做三件事：起飞、定点悬停、外部触发降落。
飞机不知道障碍在哪，也不会自己去某个地方。现在它可以。

## 三个最关键的结论

**1. 避障算法一行没改。**
移植前做了耦合度普查，结论比预期乐观：Super A\* 的策略头文件、EGO 全部 6 个子包、
`race_msgs` 消息定义，全部**零 PX4 依赖**，原样拷贝即可。真正的重写只集中在一个
文件（`offboard_waypoint_node.cpp`）的通信层。这意味着仿真里验证过的避障行为在
真机上应当一致 —— 前提是喂给它的坐标和地图是对的。

**2. px4_msgs 已从导航栈彻底移除。**
`race_offboard` / `race_ego_bridge` / `race_super_planner_ros2` / `race_mapping` /
`race_bringup` / `race_msgs` 六个包里搜不到任何 `px4_msgs` 引用。已核实。

**3. 旧的起飞基线 `minipc_mavros_offboard.py` 已删除。**
`offboard_waypoint_node` 现在是唯一的 Offboard 节点，也是
`/mavros/setpoint_raw/local` 的唯一发布者。代价见下面第 5 点。

## 定位链路一行未改

```
MID-360 → FAST-LIO → /Odometry → EV 健康监视 → /mavros/vision_pose/pose_cov → EKF2
```

这条链路已在真机验证过，本次融合完全没有触碰。三个不变式（单一 setpoint 发布者 /
单一 EV 写入者 / 杆臂只补偿一次）复核通过。

| # | 事项 | 为什么阻断 | 需要场地 |
|---|---|---|---|

## 已经永久失去的两层保护

删除 `minipc_mavros_offboard.py` 时，随之失去**水平漂移保护**和**起飞瞬态守卫** ——
它们从未移植进 `race_offboard`。这是明确接受的取舍，不是遗漏。

现在的替代手段只有：六层高度保护、EV 健康门禁，以及**操作者用遥控器随时接管**。
飞行中出现水平漂移或起飞抖动，系统不会自己反应。

**实飞必须有人握着遥控器。**

## 一条最容易犯的错

工程里同时存在三套坐标约定。看到 `frame_utils.hpp` 里的 `nedToMap = {-x, y, -z}`
会很想把它"修正"成标准的 XY 交换 —— **不要改**。`shared_safety` 整块
（geofence、0.29m 净空）都是按 `(South, East, Up)` 标定的，改约定会静默废掉所有
安全边界，而且不会有任何报错。详见 §4。

# 第二部分：详细说明

## 1. 为什么要做

`ws_offboard_control` 是真机工作区。EV 定位链路已经验证并收敛为唯一通路，但它没有
任何路径规划或避障能力。

`0807BFR` 是仿真工作区，导航能力完整，但全程走 PX4 DDS（`px4_msgs` +
Micro-XRCE-DDS Agent，UDP 8888）。真机这边是 MAVROS + 串口。两套通信机制不兼容，
不能直接拿来用。

所以工作的本质不是"写导航算法"，而是"把一套完整的导航算法从一种通信底座搬到另一种"。

## 2. 关键判断：算法本身不需要改

移植前做的耦合度普查结果：

| 组成部分 | 与 PX4 的耦合 | 处理方式 |
|---|---|---|
| Super A\* 的 6 个策略头文件 | **零**（纯 STL 数学） | 原样拷贝 |
| EGO 全部 6 个子包 | **零** | 原样拷贝 |
| `race_msgs` 三个消息定义 | **零** | 原样拷贝 |
| Super A\* 节点主体 | 只用了 1 个 PX4 消息类型 | 改约 20 行 |
| EGO 的 4 个桥接节点 | 1 个零改动，3 个换消息类型 | 改几十行 |
| `race_mapping` 5 个节点 | 只有 1 个用到，且那段默认关闭 | 删掉那段 |
| `race_offboard` Offboard 节点 | 41 处引用，arm/mode/setpoint/心跳全套 | **重写通信层** |

结论：**规划算法完全不知道 PX4 存在**。真正的工作量集中在
`race_offboard/src/offboard_waypoint_node.cpp`。

这一点是整次融合成立的前提。如果避障逻辑和飞控通信纠缠在一起，这次融合就不是
"换底座"而是"重写导航"，风险完全不同。

## 3. 移植分层

### 层 1：原样拷贝（零改动）

- `race_msgs/` —— NavigationSetpoint / LocalPathReference / GlobalPlannerStatus，
  仅依赖 `geometry_msgs` + `std_msgs`
- `ego_planner_upstream/` 全部 6 个子包（bspline_opt / path_searching / plan_env /
  plan_manage / quadrotor_msgs / traj_utils），与 `0807BFR` 逐字节一致
  - `plan_manage` 依赖 `race_msgs`（本地 fork，非上游），必须一起移
  - `traj_utils/msg/Bspline.msg` 有两个非上游字段
    `constrained_clearance` / `required_clearance`，保留
  - 编译依赖：Eigen3 + PCL + pcl_conversions + OpenCV + cv_bridge + message_filters。
    **不需要 NLopt**（这个 fork 用自带 LBFGS）

### 层 2：换消息类型（改几十行）

**`race_super_planner_ros2`** —— 只用了 `VehicleLocalPosition` 一个 PX4 类型，而
节点本来就内建完整的 `nav_msgs/Odometry` 路径。所以：

- 删掉 `prefer_px4_local_position` 参数、`px4_local_position_topic_` 成员和
  `px4LocalPositionCallback`（48 行）
- 改订阅 `/mavros/local_position/odom`，`odom_input_frame: map_enu`
- 健康闭锁从 PX4 估计器标志改为 `/mavros/state.connected`
- 输出仍写 `frame_id = "px4_ned"`，与 `race_offboard` 的内部契约保持不变

**`race_ego_bridge`** 四个桥接节点：

| 节点 | 改动 |
|---|---|
| `ego_goal_bridge.cpp` | 零改动 |
| `ego_odom_bridge.cpp` | 订阅类型换 `nav_msgs/Odometry`（订 `/mavros/local_position/odom`），转换 `nedToMap` → `enuToMap` |
| `ego_cloud_bridge.cpp` | 位姿源换 `/mavros/local_position/pose`（`geometry_msgs/PoseStamped`） |
| `ego_trajectory_bridge.cpp` | 输出换 `mavros_msgs/PositionTarget`，`mapToNed` → `mapToEnu` |

`ego_odom_bridge` 特意保留而不是让 EGO 直接订 MAVROS 话题：它会丢掉 roll/pitch
只重发 yaw，EGO 的 flat（定高巡航）模式依赖这个行为。

`ego_map_source: static_live_px4` 这个枚举串在三处都有校验，改名会连锁触发启动
throw，**故意不改名**。

**`race_mapping`** —— 5 个节点里只有 `fastlio_bridge_node.cpp` 有 PX4 分支，且由
`publish_visual_odometry_to_px4` 控制、默认 false、launch 也传 false，运行时根本
不执行。整段连参数一起删掉。

同时把硬编码的 `/fast_lio/odometry` 参数化为 `odom_topic`，默认 `/Odometry` ——
见 §8.1。

### 层 3：重写 Offboard 节点通信层

状态机逻辑一行没动：两套状态机（`State` 7 态 + `ControlState` 8 态）、
`runActive()` 的 10 级优先级链、六层高度保护，全部原样保留。
`takeoff_handover_policy.hpp` 和 `ego_command_guard.hpp` 两个纯逻辑头文件零改动。

只换通信层：

| 原 PX4 DDS | 换成 MAVROS |
|---|---|
| `OffboardControlMode` 心跳发布 | **整体删除** —— MAVROS 自己维护心跳 |
| `TrajectorySetpoint` × 3 处 | `mavros_msgs/PositionTarget` → `/mavros/setpoint_raw/local` |
| `VehicleCommand` ARM(400) | `/mavros/cmd/arming` 服务（CommandBool） |
| `VehicleCommand` DO_SET_MODE(176) | `/mavros/set_mode` 服务，custom_mode=`OFFBOARD` |
| `VehicleCommand` NAV_LAND(21) | `/mavros/set_mode`，custom_mode=`AUTO.LAND` |
| `VehicleLocalPosition` 订阅 | `/mavros/local_position/pose` + `velocity_local` |
| `VehicleStatus` 订阅 | `mavros_msgs/State`（新增 `connected_`） |

### 层 4：不移植

- `FAST_LIO` —— 真机用 `~/livox_mid360_env/ws_fastlio` 的预编译二进制（既定约束）
- `livox_ros_driver2` —— 真机已有
- `mid360_simulation`、`race_world` —— 仿真件
- `PX4-Autopilot`、`Micro-XRCE-DDS-Agent` —— 真机走 MAVROS 串口
- `Lin_shi/` —— Nav2 线已退役，不参与构建

## 4. 三套坐标系（最危险的部分）

工程里现在同时存在三个不同的坐标约定。轴搞反了飞机会朝错误方向飞，而集成测试
发现不了 —— 这是全部改动中最需要小心的地方。

| 名字 | 轴向 | 谁在用 |
|---|---|---|
| 项目 `map` 帧 | **(South, East, Up)** | 规划器内部、geofence、点云地图、`mission.yaml` |
| `px4_ned` | 标准 NED (North, East, Down) | `NavigationSetpoint` 消息、Offboard 节点内部状态 |
| MAVROS ENU | 标准 ENU (East, North, Up) | `/mavros/local_position/*`、`/mavros/setpoint_raw/local` |

`map` 帧**不是** ENU。它由 `race_ego_bridge/frame_utils.hpp` 里
`nedToMap = {-x, y, -z}` 定义，展开后是 (South, East, Up)，与标准 ENU 相差绕
Up 轴 −90°。

### 坑一：`FRAME_LOCAL_NED` 其实要填 ENU

`/mavros/setpoint_raw/local` 的 `coordinate_frame` 常量名叫 `FRAME_LOCAL_NED`，
但 MAVROS 插件内部会自己做 ENU→NED 再发 MAVLink。**所以这里必须填 ENU 数值。**

把 NED 原样填进去 → North 和 East 互换 → 飞机朝 90° 偏的方向飞。

### 坑二：不要"修正" `nedToMap`

看到 `{-x, y, -z}` 会很想把它改成标准 XY 交换。**不要改。**

`astar_ego_tuning.yaml` 里 `shared_safety` 整块都是按 (South, East, Up) 标定的：

```yaml
shared_safety:
  required_center_clearance: 0.29
  geofence:
    x_min: -0.85    x_max: 11.90
    y_min: -1.30    y_max: 12.40
    z_min:  0.50    z_max:  0.85
    boundary_margin_m: 0.15
```

改约定会静默废掉所有安全边界，不报错。

### 怎么防住

转换只发生在一个地方 —— `race_offboard` 的 MAVROS 边界，集中在
`race_offboard/include/race_offboard/mavros_frame_utils.hpp` 的 4 个函数：

```cpp
enuToNed({e,n,u})  -> {n, e, -u}
nedToEnu({n,e,d})  -> {e, n, -d}
enuYawToNed(yaw)   -> wrap(π/2 - yaw)
nedYawToEnu(yaw)   -> wrap(π/2 - yaw)
```

配套 11 个 gtest（`test_mavros_frame_utils.cpp`）覆盖往返恒等、跨 ±π 环绕、
基本方向（ENU yaw 0 = 东 = NED yaw 90°）。

其中两个测试是**跨包一致性交叉验证** —— 在测试文件里故意重新实现一份
`nedToMap`，验证 `enuToMap == nedToMap(enuToNed(·))`。如果两个包的约定哪天漂移了，
测试会红。这份重复是刻意的：用共享 include 反而会把不一致藏起来。

## 5. Offboard 节点的三个非平凡改动

不只是"换个消息名"的三处：

### 命令从发布变成服务调用

PX4 DDS 的命令是 fire-and-forget 发布；MAVROS 全是服务。在 20Hz 定时器回调里
同步 `call()` 会死锁执行器。

改成 `async_send_request` + 回调 + pending 标志跟踪。原有的 1s 节流重试逻辑保留，
但加了 future pending 判断避免重复请求。**这是本次最大的结构性改动。**

### "忽略某轴"的表达方式变了

PX4 用 NaN 标记被忽略的轴，MAVROS 用 `type_mask` 位掩码。

不能用固定掩码：超高软守卫只把 Z 轴前馈置 NaN，要保留 XY 前馈。所以掩码必须
**逐轴动态生成**：

```cpp
positionTargetTypeMask(velocity_enu, acceleration_enu, yaw_rate_valid)
// 每个轴 NaN → 置对应 ignore 位
```

配套 `sanitizeIgnoredAxes()` 把被忽略轴的 NaN 换成 0 —— MAVROS 某些路径不看掩码
直接转发字段值，MAVLink float 里的 NaN 比一个被掩掉的 0 更危险。

另外 `PositionTarget` **没有 jerk 字段**，EGO 的 jerk 前馈会丢失（其他路径的
jerk 恒为 NaN，所以只影响 ego 透传）。

### 定位健康标志位没有等价物

PX4 的 `VehicleLocalPosition` 带 4 个估计器有效性标志
（`xy_valid` / `z_valid` / `dead_reckoning` / `heading_good_for_control`），
MAVROS 的 pose 消息什么都不带。

采用保守等价：有限、单调、通过跳变检查的 pose 就视为有效；同时把 MAVROS 独有的
`State.connected` 纳入守卫 —— 这是 PX4 DDS 没有的信号，能检测串口链路断开。

因为 `require_strict_local_position_health` 本来默认 false，这与原行为等价，
没有行为回退。

## 6. 新增：EV 健康门禁

`race_offboard` 原本完全没有 EV/vision 健康检查（穷尽检索确认过）。仿真里不需要 ——
PX4 SITL 的位置估计永远有效。

真机不一样：EKF2 的位置来自 FAST-LIO 经 `/mavros/vision_pose/pose_cov`，这条链路
可能在 MAVROS 报告链路健康的同时悄悄退化。**在退化的外部视觉估计上解锁**就是这个
门禁要防的事故。

从已飞过的 `minipc_mavros_offboard.py` 移植 `EvHealthTracker`（改写为 C++
header-only，时间以纳秒计数传入，便于脱离 ROS 单测），行为一致：

**起飞前**
- 连续 `HEALTHY` ≥ 7.5s 才允许解锁
- `SUSPECT` 一次就**重置整个计时**，不是暂停 —— 已累积的 7 秒不予保留
- 消息中断超过新鲜度窗口（1.0s）也重置

**飞行中**
- 只有 `FAULT` 触发 `AUTO.LAND`
- `SUSPECT` 和状态超时会记录但不单独降落（与已飞行为一致）

**无法识别的状态字符串按 `FAULT` 处理**，不按"大概没事"。

参数：`require_ev_health`(true) / `ev_health_topic`(`/ev_health/status`) /
`ev_health_required_s`(7.5) / `ev_health_freshness_s`(1.0)。
配套 11 个 gtest（`test_ev_health_tracker.cpp`）。

### 同时删掉了 force_arm

`force_arm_in_sim`（PX4 magic 21196）**已删除**。它绕过 PX4 预飞检查，仿真调试
方便，真机上误开会跳过安全检查。真机必须让预飞检查生效。

## 7. 竞赛任务链

融合初期只搬了"导航与避障"，竞赛任务链是断的。现已接上：

| 原状态 | 现状态 |
|---|---|
| `planner_backend` 默认 `ego-shadow`（EGO 并行但不控制，诊断模式） | 默认 `astar_ego`（比赛配置） |
| `mission_enabled` 默认 `false`（任务序列器不启动） | 默认 `true` |
| 四个航点只能 RViz 手点 → 无人值守跑不了 | 支持 `mission.yaml` 的 `preset_points`；RViz 点击仍可当天覆盖 |
| 识别触发信号无任何订阅者（只打日志） | 发布 latched `/race/mission/recognition`，新增 `bs_recognition_node.py` 消费 |

任务流：

```
mission_sequencer  ──/goal_pose──────────→ Super A*
（A→B1→B2→C→D）    ──/race/mission/zone──→ 诊断/录包
                   ──/race/mission/recognition (latched)
                                          ↓
                              bs_recognition_node
                            （urgb.py 四模型级联，仅在
                              B/D 区识别开启时运行）
                                          ↓
                              /race/recognition/result
```

`bs_recognition_node.py` 复用 `urgb.py` 的四模型级联（不复制推理代码，阈值不变），
延迟到首次需要时才 import 和开相机 —— 加载四个 YOLO 模型要几秒并占满 CPU，放在
构造函数里会拖慢整个 bring-up。默认**不随 launch 启动**
（`recognition_enabled:=false`）：RealSense 和 YOLO 权重缺失不应该在飞行中才发现。

注意 `urgb.py` 在 import 时会 `sched_setaffinity` 把进程钉到 3 个核，这会影响整个
ROS 进程（含执行器）而不只是推理。节点已把 `cpu_threads` / `cpu_limit` 暴露为参数
并在 import 前设置环境变量，`cpu_limit:=0` 可完全关闭钉核。

`preset_points` 当前在 `mission.yaml` 里是**注释掉的占位坐标**（来自仿真场地），
必须换成实测坐标才有意义。坐标是项目 map 帧 (South, East, Up)，不是标准 ENU，
填写前先读 §4。

## 8. 顺手修掉的三个会导致启动即崩的问题

这三个不是移植引入的，是移植过程中暴露出来的。

### 8.1 话题名不匹配（静默失效，最阴的一个）

`fastlio_bridge_node.cpp` 曾硬编码订阅 `/fast_lio/odometry`，而真机 FAST-LIO
（`~/livox_mid360_env/ws_fastlio`）实际发布 `/Odometry`。

这个节点会**一条消息都收不到**，`/race/odom` 与 `/race/pose` 永不发布，**且不报错**。

已参数化为 `odom_topic`，默认 `/Odometry`；启动日志会打印实际订阅的话题名，
便于现场确认。

### 8.2 硬依赖不存在的 `fast_lio` 包

`race_mapping.launch.py` 在构建 launch description 时调用
`get_package_share_directory('fast_lio')`。本工作区**故意没有移植 FAST-LIO**
（真机用预编译二进制，这是既定约束），所以这个包不存在，launch 直接抛
`PackageNotFoundError`。

已改为可选（`start_fast_lio` 参数，默认 false，包裹 try/except）。

### 8.3 5 处硬编码 `use_sim_time: True`

真机没有 Gazebo `/clock`，节点会永久等待一个永远不来的时钟。已全部改为参数驱动，
默认 false。

## 11. 实飞前必须关闭的项目

### 11.1 阻断级：速度坐标系错误（代码已确认有误）

`ego_odom_bridge.cpp:58-62` 假设 `/mavros/local_position/odom` 的 `twist.twist.linear`
在 **world ENU** 系，但 MAVROS 源码确认它是 **body frame (FLU)**。

当前代码直接用 `enuToMap(velocity_enu)` 只做了绕 Up 轴旋转，没有 body→world 的姿态
旋转。**一旦飞机转向，EGO 收到的速度方向就错了**。B-spline 优化器依赖当前速度作为
边界条件，方向错会导致转弯时轨迹扭曲或抖动。

**修复方式**（`ego_odom_bridge.cpp` 第 61-62 行附近）：

```cpp
// 错误版本：
const race_ego_bridge::Vec3 velocity_enu{
  msg->twist.twist.linear.x, msg->twist.twist.linear.y, msg->twist.twist.linear.z};

// 正确版本：先从 body 转到 world
tf2::Quaternion q;
tf2::fromMsg(msg->pose.pose.orientation, q);
tf2::Matrix3x3 body_to_world(q);
tf2::Vector3 velocity_body(
  msg->twist.twist.linear.x, msg->twist.twist.linear.y, msg->twist.twist.linear.z);
tf2::Vector3 velocity_world = body_to_world * velocity_body;

const race_ego_bridge::Vec3 velocity_enu{
  velocity_world.x(), velocity_world.y(), velocity_world.z()};
```

然后第 79 行的 `enuToMap(velocity_enu)` 继续保留。

**影响范围**：悬停时看不出问题（yaw=0 时 body 与 world 对齐），执行需要转弯的路径时
才暴露。详见 `验证方法.md` §2。

### 11.2 阻断级：geofence 与高度是仿真场地值

当前 geofence：x ∈ [−0.85, 11.90]、y ∈ [−1.30, 12.40]，即 **12.75m × 13.70m**。
竞赛场地是 **15m × 14m**。这组数值来自仿真赛场模型标定，**不是真实场地实测**。

更要紧的是高度：z ∈ [0.50, 0.85]，巡航 0.78m。而现有已验证的真机起飞基线是
**0.80m** —— 恰好在 0.85 上界附近，余量只有 5cm。超高软守卫在 1.05m 触发。

**这是安全合同，必须现场实测重标，不能沿用仿真值。**

## 13. 怎么启动

```bash
cd ~/rong_ws/ws_offboard_control

# 编译
source /opt/ros/humble/setup.bash
colcon build --packages-up-to race_offboard
source install/setup.bash

# 一键启动完整硬件链（MID-360 + FAST-LIO + MAVROS/EV + rosbag + 导航）
MAP_FILE=/path/to/arena.pcd ./tools/flight/一键启动导航栈.sh

# 拆桨链路验证，不加载地图、不启用任务或导航输出
NO_MAP_VALIDATION=true ./tools/flight/一键启动导航栈.sh

# 只启动已运行 MAVROS/EV 的导航进程（调试/复现用）
MAP_FILE=/path/to/arena.pcd ./tools/flight/运行导航控制.sh

# 带识别（需 RealSense + YOLO 权重）
RECOGNITION_ENABLED=true MAP_FILE=... ./tools/flight/运行导航控制.sh

# 诊断模式：EGO 并行运行但不控制飞机
PLANNER_BACKEND=ego-shadow ./tools/flight/运行导航控制.sh
```

环境变量：`PLANNER_BACKEND`（astar_ego / super / ego / ego-shadow）、
`MISSION_ENABLED`、`MAP_FILE`、`RVIZ`、`RECOGNITION_ENABLED`。
