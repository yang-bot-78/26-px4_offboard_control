# 门禁拓扑与故障传播

> 更新时间：2026-08-16

本轮改的是**门禁动作和故障传播关系**，不是阈值。全部阈值改动只有两处，都在
§4 单独列出并给出依据。

## 1. 改造前的故障级联

```text
LiDAR 慢 200ms
→ anchor_age > 0.40s
→ HighRateOdomResult.publish = false     ← /Odometry 断流
→ EV monitor: frlio_status_FAULT_STALE_LIDAR, block_output = true
→ /Odometry/healthy 断流 → PX4 退出 EV 融合
→ offboard: frlio_fault_hold_latched_ = true, goal_active_ = false
→ 任务永久取消，必须人工重启导航栈
```

一个 200ms 的 LiDAR 抖动会走完整条链。每一层都在**重复判断同一个事实**
（"LiDAR posterior 旧了"），却各自升级成更严重的动作。

## 2. 改造后的分层

两条**互相独立**的健康轴，合成一个快照：

| 轴 | 判据 | 能达到的最高等级 |
| --- | --- | --- |
| anchor（LiDAR posterior 年龄） | `anchor_age` | **L2 PLANNER_UNUSABLE** |
| predictor（IMU 传播状态） | `predictor_age`、时间戳回退、NaN/Inf、未初始化 | **L3 STATE_UNUSABLE** |

```text
                  anchor 轴                predictor 轴
                      │                         │
                      └────── max（取更严重）────┘
                                  │
                    LocalizationHealthSnapshot
                                  │
                    ┌─────────────┴─────────────┐
                ev_usable                planner_usable
                    │                          │
              /Odometry 继续              EGO 是否允许换轨迹
                    │                          │
              EV monitor                  offboard planner hold
                    │
              PX4 EKF2 自己决定是否融合
```

| 等级 | status 字符串 | ev_usable | planner_usable | 触发 |
| --- | --- | --- | --- | --- |
| L0 GOOD | `HEALTHY` | 是 | 是 | `anchor_age < 0.18s` |
| L1 DEGRADED | `SUSPECT_STALE_LIDAR` | 是 | 是（协方差放大） | `anchor_age > 0.18s`，回落 `< 0.12s` |
| L2 PLANNER_UNUSABLE | `FAULT_STALE_LIDAR` | **是** | 否 | `anchor_age > 0.40s` |
| L3 STATE_UNUSABLE | `FAULT_STATE_UNUSABLE` | 否 | 否 | `predictor_age > 0.15s` / 时间戳回退 / NaN / 未初始化 |

关键不变式（有单元测试固定）：

```text
anchor_age = 0.8s, predictor_age = 0.02s
  → ev_usable = true, planner_usable = false
planner_usable = true 必然 ev_usable = true
anchor 轴任何数值（含 NaN、5s）都到不了 L3
```

一致快照：所有字段（`steady_clock_now`、`sequence`、`anchor_age_s`、
`predictor_age_s`、`imu_backlog_age_s`、`imu_queue_size`、
`posterior_generation`、`predictor_generation`、`timestamp_monotonic`、
`state_finite`、`position_jump`、`velocity_jump`、`level`、`reason`、
`ev_usable`、`planner_usable`）在同一时刻取，一次发布。
`HEALTHY + anchor_age=1.1s` 这种矛盾组合不可能出现。

## 3. 删除/放宽的硬门禁 —— 保护由谁承担

### 3.1 `HighRateOdomResult.publish = false`（anchor_age > 0.40s）

`high_rate_odom.hpp` 原来在 anchor 过旧时把 `publish` 置假，`/Odometry` 直接断流。

**现在**：`publish` 只在 `state_finite == false` 时为假。

失去的保护由三层承担：

1. **协方差放大**（同层，原有机制）：`stale_covariance_growth_per_s=4.0`，
   上限 `stale_covariance_max_multiplier=100`。发出去的是真实传播状态，但
   协方差如实反映"正在纯 IMU 递推"。
2. **PX4 EKF2**（下游，本来就有）：EV innovation 检验、EV timeout、fusion
   reset、local position validity。协方差变大后 EKF2 会自动降低 EV 权重，
   这本来就是它的职责，上游断流只是替它做了决定还做得更差。
3. **planner_usable = false**（横向）：真正需要阻止的是"拿漂移的位姿去规划
   新轨迹"，这个由 planner 侧门禁精确承担，不需要牵连 PX4。

新增的替代保护：`PredictorHealthGate` 现在会在 predictor 真的失效时把
`ev_usable` 置假 —— 这是原来**没有**的检查。原实现只检查 anchor，
一个 predictor 卡死但 anchor 恰好新鲜的状态会被判为 HEALTHY 放过去。

### 3.2 EV monitor 的 `frlio_anchor_stale` 硬 block

`_evaluate_frlio_anchor_gate` 原来在 `anchor_age >= max_anchor_age_s` 时
无条件 `block_output = true`。

**现在**：走与 `FAULT_STALE_LIDAR` 相同的分级路径 —— 先校验 predictor 新鲜度，
predictor 新鲜则 `block = False` 并标记 degraded。

失去的保护由：

1. **predictor 新鲜度校验**（同函数内）：`_predictor_reason()` 仍然会在
   predictor 缺失/超时/过旧时 block。license 从"anchor 新"改成了
   "predictor 新"，而 predictor 新才是"当前状态可信"的正确判据。
2. **协方差放大**：`frlio_degraded_covariance_multiplier = 100.0` 仍生效。
3. **`flight_ready = False`**：`_evaluate_flight_ready` 的
   `frlio_predictor_degraded` 分支不变，degraded 状态下起飞前门禁仍然关闭。
4. **PX4 EKF2**：同 3.1。

顺带修掉一个竞态：anchor_age 越过阈值和携带该转换的 status 消息不同步到达，
原实现会因消息顺序制造一次 EV 断流。

### 3.3 `frlio_fault_hold_latched_` 永久闭锁 + `goal_active_ = false`

原实现收到一条 `FAULT_STALE_LIDAR` 就永久取消任务，`[FRLIO_RECOVERED]` 日志
明确写着"remaining in hold until navigation is explicitly restarted"。

**现在**：`frlio_planner_hold_active_` 可恢复，且**不再动 `goal_active_` 和
`navigation_cancelled_`**。

失去的保护由：

1. **hold 本身不变**：仍然 `beginBraking(PLANNER_FAILURE_HOLD)`，仍然拒收新
   setpoint（`egoSetpointCallback` / `navigationSetpointCallback` 双入口拦截），
   仍然在 `runActive` 里持续 `publishLockedHold()`。飞机行为完全一样。
2. **释放条件是三重的**：FR-LIO 报告 planner 可用 **且** 已稳定
   `frlio_hold_release_stable_sec=1.0` **且** 水平速度 ≤
   `hold_velocity_tolerance`。速度不达标就重置稳定窗口。
3. **恢复后不接旧轨迹**：释放时置 `awaiting_initial_ego_trajectory_ = true`，
   必须等新验证轨迹，旧轨迹不允许续跑。
4. **需要操作员介入的类别仍然只能由操作员清除**：
   `planner_safety_failure_latched_`（EGO 安全闭锁，只在显式新目标或
   `/race/cancel` 时清除）、`pilot_override_latched_`（重启导航栈才清除）、
   `collision_latched_` 都没动。本轮只把"LiDAR posterior 变旧"这一个**可自愈**
   的原因从这一类里移出去。
5. **`frlio_hold_release_enabled: false`** 可退回原行为。

判断依据：LiDAR posterior 变旧是**可自愈**的（下一帧 posterior commit 就恢复），
用不可恢复类别的手段处理可恢复故障，本身就是故障传播放大。

### 3.4 EGO 轨迹切换里的耦合判据

原实现用一个 `transitionStateContinuous(last_valid_output_, candidate)` 同时
回答了两个问题，并且两个都用"拒绝轨迹"来响应。

**现在**拆成：

```text
splice_error   = candidate(t_switch) vs bridge 当前输出的轨迹
                 → 唯一可以拒绝候选轨迹的判据（阈值、行为都没变）
tracking_error = 实测位置 vs 当前正在跟踪的指令
                 → 只上报，不拒绝
```

`classifyTrajectoryFault` 给出四种诊断：`TRAJECTORY_HANDOFF`（splice 大 tracking 小）、
`LOCALIZATION_TRACKING`（splice 小 tracking 大）、`Both`、`None`。

这里**没有放宽任何门禁**：splice 判据的阈值和拒绝动作原样保留，只是新增了
tracking 维度的上报。tracking 大不拒轨迹的理由是：跟踪误差是定位/控制问题，
拒掉替换轨迹反而拿走了唯一能减小该误差的手段。

## 4. 阈值改动（仅两处，均有依据）

| 参数 | 原值 | 新值 | 依据 |
| --- | --- | --- | --- |
| `frlio_max_predictor_age_s`（EV monitor） | 0.05 | 0.15 | 已测 high-rate publish gap max = 135ms（`保护门.md` §10）。0.05s 在健康运行时就会触发。且必须与 fr_lio 的 L3 阈值一致，否则两层对"状态何时不可用"的判断互相矛盾。 |
| `high_rate_odom.max_predictor_age_s`（新增） | — | 0.15 | 同上；要求文档 §3 给的范围是 100~150ms，取上界配合 135ms 实测 gap。 |

`anchor_age` 相关阈值（0.18 / 0.12 / 0.40）**一个都没改** —— 300s 静置分布
（P50 93.3ms / P95 142.3ms / P99 147.4ms / max 232.5ms）支持现有取值。

## 5. Offboard 心跳：planner HOLD ≠ Offboard 断流

审计发现三条会让 setpoint 流中断的路径，全部补上 keepalive：

| 路径 | 原行为 | 现行为 |
| --- | --- | --- |
| `publishSafetySetpoint`（`!hold_position_valid_`） | 直接 return，不发 | `publishOffboardKeepalive()` |
| `runBraking`（无 hold 点） | 直接 return | 同上 |
| armed IDLE 无 hold（拒绝自动重锁） | 只发诊断 | 同上 |

`publishOffboardKeepalive` 只在 `armed_ && offboard_mode_ && last_command_valid_`
时重发**上一条已被接受的 setpoint**。这是重发指令，不是重发状态估计 ——
"不用旧状态冒充新状态"的约束没有被破坏。

FR-LIO hold 分支在 `runActive` 里每个 tick 都调用 `publishLockedHold()`，
所以 `planner_usable=false` 期间 PX4 侧的 20Hz setpoint 流完全连续。

## 7. 保留未动的语义

- `restamp_message = false`：未改。
- delayed LiDAR correction / IMU replay：`reset_from_lidar` 的
  短锁 snapshot → 锁外 replay → generation/timestamp 校验 → 短锁 commit
  流程逐行未动。
- 不伪造 timestamp、不用旧状态冒充新状态：未破坏（见 §5）。
- PX4 EKF2 自身保护：未删任何一项，反而更依赖它。
- mutex 优化不是本轮重点，未回退（`mutex_hold` P95 = 56us 保持）。

### 8.1 已在本机实跑的项

**predictor watchdog（无硬件，合成 IMU）**：以 200 Hz 喂 3s 合成 IMU 后停止，
观测 `/frlio/high_rate_odom/` 三个话题：

```text
status         → FAULT_STATE_UNUSABLE，停流后 0.151s 首次上报，并持续重发
ev_usable      → false
planner_usable → false
localization_health: level=STATE_UNUSABLE, reason=not_initialized,
                     predictor_age_s 持续增长, state_finite=false
```

结论：watchdog 生效，IMU 完全停止时状态**不会**停在 latched 值。
但这一轮 `reason=not_initialized`（无 LiDAR，从未建立 anchor），所以它证明的是
"没有状态"这条路径，**不是** GOOD → L3 的转换。后者需要 Test C。

### 8.4 本机实时路径优化

- 飞行配置 `indoors.yaml` 默认关闭逐样本 `FRLIO_TIMING` 日志；高频验收脚本通过
  `timing_alignment_enabled:=true` 显式开启，取证配置不会意外进入飞行。
- `correct_working_tree=false` 的飞行路径不再在 OpenMP k-NN 的每个点上抢
  `mtx_ikdtree`。只有启用后台 working-tree 重建时才保留该锁；不得用截断 IMU 队列
  的方式掩盖处理延迟。
- `一键启动导航栈.sh` 和 `验证高频里程计全链路.sh` 默认锁定本机
  `powerprofilesctl performance`，并校验所有 CPU policy 的 EPP。退出时仅在本次确实
  修改过 profile 且链路可安全停止时恢复原 profile；若飞控状态无法确认上锁，链路和
  performance profile 都保持不变。

回归验收仍看 LiDAR processing、`imu_queue`、高频输出 gap 和 predictor age；优化目标是
降低处理峰值，而不是放宽队列门禁或丢弃 delayed-correction 所需的 IMU 样本。

`fr_lio` 本地 Release 编译通过；`test_high_rate_odom` 为 32/32，
`test_map_correction` 为 9/9。全工作区测试仍受上游 `ego_planner_upstream` 的既有
lint/package.xml 问题影响，不能作为本任务的失败依据。

### 8.3 Test C 注入工具（本轮新增）

原来没有能让 predictor 停顿的工具：LiDAR gate 只能饿死 posterior，那按设计是
L2、EV 必须继续，永远走不到 L3。也就是说**唯一还允许断 EV 的那个门禁此前没有
整机测试手段**。

新增 `fr_lio/imu_validation_gate`（`src/imu_validation_gate.cpp`），接口与
LiDAR gate 一致：

```bash
# 让 FR-LIO 读门控后的 IMU（改 config 的 common.imu_topic）
ros2 run fr_lio imu_validation_gate --ros-args \
  -p input_topic:=/livox/imu -p output_topic:=/validation/livox/imu

# 暂停 / 恢复
ros2 service call /frlio_validation/imu_gate std_srvs/srv/SetBool "{data: false}"
ros2 service call /frlio_validation/imu_gate std_srvs/srv/SetBool "{data: true}"
```

它原样转发（不改时间戳、不合成替代样本），暂停期间预期：

```text
status         → FAULT_STATE_UNUSABLE
reason         → predictor_stale（而不是 not_initialized）
ev_usable      → false
恢复后需 predictor_generation 递增 + 连续 3 个新鲜样本才回 GOOD
```

该节点**不进飞行图**：FR-LIO 正常直接订阅 `/livox/imu`，只有验证场次才 remap。

### 8.4 B/C 硬件整机结果

B 使用验证门控对每帧 LiDAR 保持原 timestamp 和 payload，仅把到达 FR-LIO 的时间
延迟 300ms。4s 延迟窗口内最大 anchor age 为 488.5ms，状态达到
`PLANNER_UNUSABLE/anchor_stale`，但所有健康快照均为 `ev_usable=true`，
predictor age 保持新鲜，`/Odometry` timestamp 最大间隔 13.2ms。关闭延迟后恢复
`GOOD`。同一故障窗口内 `/Odometry/healthy` 有 681 条（169.2Hz，最大录包间隔
15.0ms），`/mavros/odometry/out` 有 173 条（43.0Hz），证明 backend 延迟和
planner 不可用都不会升级成 EV/PX4 定位断流。

C 在 predictor generation=14290、系统已经 GOOD 后暂停门控 IMU 1s。首个 L3
快照出现在 predictor age=150.2ms，原因是 `predictor_stale`，`ev_usable=false`、
`planner_usable=false`；停止窗口仅有 2 条门控切换前已在途的 `/Odometry`。恢复 IMU
后 predictor generation 前进到至少 14415，并经过 3 个新鲜快照后恢复 GOOD。

第一次 C 实跑还发现 watchdog 把已初始化的 predictor 静默硬编码成
`not_initialized`。现在 watchdog 保存最后一次有效 predictor generation，并把有限但
过旧的状态报告为 `predictor_stale`；未初始化和非有限状态仍走各自独立原因。

## 9. 顺带修掉的实际缺陷

`laser_mapping.cpp` 原代码在 StaleLidar 时先发 `FAULT_STALE_LIDAR`，紧接着
**无条件**再发一次 `health == Suspect ? "SUSPECT_STALE_LIDAR" : "HEALTHY"`：

```cpp
if (health == StaleLidar) { publish_high_rate_status("FAULT_STALE_LIDAR"); ... }
publish_high_rate_status(health == Suspect ? "SUSPECT_STALE_LIDAR" : "HEALTHY");
```

StaleLidar 期间 status 以 200Hz 在 `FAULT_STALE_LIDAR` 和 `HEALTHY` 之间交替
（250ms 去重只压制**相同**字符串的重复，交替值全部放行）。下游看到的绝大多数
是 `HEALTHY`，而 offboard 侧"一条 FAULT 就永久闭锁"的设计正是为了抓住这个
脉冲 —— 两个缺陷互相掩盖。现在整个 IMU 回调只有一处 status 发布点，取自
同一个快照。

另外补了两个漏洞：

**`if (!result) return;` 静默返回**：status 停在上一个 latched 值。predictor 未
初始化或样本被判非单调时，一个"没有当前状态"的 FR-LIO 在下游读起来仍是
`HEALTHY`。现在这条路径也发快照，等级为 L3。

**IMU 完全停止时无人上报**：健康快照原本只在 IMU 回调里产生，IMU 一停回调就不
再触发，status 会永久停在最后一次的值 —— 恰好就是 Test C 的场景。新增
`check_predictor_watchdog()` 挂在独立的 100 Hz 主定时器上，是唯一能报告
"完全没有 IMU"的路径。已在本机用合成 IMU 验证（§8.1），停流后 0.151s 上报。

watchdog 引入的跨线程访问已处理：`last_imu_arrival_steady_s_` 改成
`std::atomic<double>`（IMU 线程写、定时器线程读）；`publish_localization_health`
和 `publish_high_rate_status` 现在由 `health_publish_mutex_` 保护，否则两个线程
交错会发出互相矛盾的 status 字符串 —— 正是 §9 开头那个缺陷的翻版。
